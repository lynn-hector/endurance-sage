# TAPD 缺陷单查询（tapd-inspector）

## 定位与使用边界

缺陷单是人工维护的背景证据，不是实时观测面。它适合回答：

- 当前症状是否与已有缺陷的描述、影响范围和条件吻合。
- 候选缺陷当前状态、处理人、解决方案和修复人是什么。
- 故障窗口内是否出现多张相似缺陷，可作为用户侧感知的间接证据。
- 已有修复方案时，对应版本是否已经部署。

以下场景使用：用户明确要求查询缺陷；症状、服务或错误文本与已知缺陷线索相关；或已有修复单需要与部署时间线对账。不要对每个新症状无目标查询 TAPD，也不要用缺陷单替代日志、链路和指标。

## 工具

`sentry_query_tapd` 为只读工具，两种模式：

| 模式 | 参数 | 返回 |
|---|---|---|
| 列表 | 省略 `id`，使用 `status/severity/owner/title/createdStart/createdEnd/limit` | 工单摘要，含 id/title/status/severity/owner/created/modified，modified 倒序 |
| 详情 | `id` | 完整工单，含 description/resolution/fixer/deadline 等 |

## 推荐排查动作

1. **寻找候选已知缺陷**：有明确线索时，用服务名或高区分度症状做 `title` 模糊匹配，必要时加故障时间窗。
2. **读取详情核对**：标题命中只代表候选，必须继续核对 description 中的症状、版本、触发条件和影响范围，不能直接认定同一根因。
3. **观察集中上报**：按 `createdStart` 等条件查看故障窗口内是否有相似缺陷，作为影响面的间接证据。
4. **核查修复状态**：对 in_progress / resolved 等候选单读取 resolution，并与 Zadig 的分支、版本和部署时间对照，确认修复是否实际生效。

缺陷单说“已修复”不等于线上已经恢复；状态、人工描述和部署结论都需要与运行时观测交叉验证。

## 边界与已知限制

- TAPD 是平台级数据源，不随 Session 环境切换；`workspaceId` 固定在装配配置中。
- **权限模型（实测 2026-08）**：经典 `/bugs/list`、`/bugs/get` 端点要求企业级 API 权限，个人令牌会返回 403；`/bugs` 端点配合 MCP 通道标记（`Via: mcp` 与 `s=mcp`）允许个人令牌读取。service 层已固定走 MCP 通道。
- 若仍返回 403，说明令牌或项目成员身份存在问题，应如实保留错误证据，不用 count 等边缘接口的数据冒充缺陷内容。
- 时间字段是 TAPD 本地格式字符串，入参支持 `YYYY-MM-DD` 或完整时间；与日志、指标的 UTC 锚点对账前先确认时区。
- 缺陷单内容可能过期或描述不准确，结论中应引用缺陷 id、状态和具体匹配依据，而不是只写“已知问题”。
