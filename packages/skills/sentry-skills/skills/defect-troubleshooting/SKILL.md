# 缺陷排查方法论

用于「现象明确但根因不清」的缺陷排查。告警卡片优先走 `alert-analysis`，跨服务延迟可叠加 `cross-service-latency`；各 inspector / analyzer 负责收集证据，`incident-templates` 负责正式输出。

这 10 步是**内部分析检查表，不是必须逐项展示的报告模板**。简单问题可以合并步骤，无关步骤可以省略；事实与假设分离、根因确认后再给确定结论这两条不能省略。不得为了填满步骤编造信息或假设。

## 1. 工作原则

1. **先界定，再下探**：先确认症状、时间、环境和影响范围，避免在错误环境或时间窗中收集证据。
2. **用验证收敛假设**：优先执行低成本、高区分度、只读的检查；每次查询都要说明它支持或推翻什么。
3. **区分关联与因果**：用时间线、请求链路和依赖方向验证因果，不因事件同时发生就认定互为原因。
4. **先止损，后修复**：紧急场景先提供可逆的止损选项，长期修复仍以根因为依据。
5. **验证一次只改变一个变量**：避免多个动作同时发生导致结果无法归因。需要改变状态时交由人类执行。

## 2. 10 步分析框架

### 2.1 缺陷描述

用「操作 / 期望 / 实际」描述现象，并记录环境、时间范围、发生频率、影响对象和严重程度。

- 已知信息不足时标为「未知」，说明它还影响什么判断。
- 严重程度可以根据现有影响暂定；没有依据时不得编造 P0–P3 或影响比例。

### 2.2 已知事实

只记录有直接来源的观察，并附可定位的引用：工具 evidence、日志行、traceId、指标查询、截图或代码位置。

用户反馈可以作为事实来源，但应写成「用户反馈出现了什么」，不能直接升级为技术根因。

### 2.3 未知信息

只列会影响当前判断的未知项，并说明其影响。通用但不影响下一步的背景问题不列入。

### 2.4 可能原因列表

根据事实建立可解释的假设，每项包含：依据、当前置信度，以及它如何解释主要症状。

- 假设数量由证据决定，不为凑数制造低价值选项。
- 多个原因都能解释症状且尚未排除时，保留主要竞争假设。
- 证据直接指向一个原因时，可以只保留一个，但仍要检查关键反证。

### 2.5 验证方法

为每个待验证假设写清：

1. **数据源与查询范围**：查哪里、什么时间窗、哪个服务或请求。
2. **判断标准**：出现什么结果支持它，出现什么结果削弱或排除它。
3. **成本与风险**：优先只读、低成本、能区分竞争假设的方法。

不能只写「检查日志」「排查数据库」。具体验证手段见 [验证方法工具箱](references/investigation-toolbox.md)。

### 2.6 推荐排查顺序

按「区分度 × 可能性 ÷ 成本」排序，同时考虑线上风险。通常先确认环境和时间窗，再查全局指标与近期变更，随后下钻代表性失败请求。

每轮证据返回后重新排序，不机械执行已经失去价值的后续步骤。

### 2.7 需要补充的信息

证据无法自行获取且会阻塞判断时，列明：需要什么、为什么需要、由谁或从哪里获取。非阻塞信息作为未知项记录，不中断当前排查。

### 2.8 可能的修复方向

根因确认后才能给出确定的根因修复建议；此前如确需止损，应明确标注为「候选止损方案」，说明依据、适用条件和风险，不得宣称已经根治。

每个方案至少包含：影响范围、验证标准；涉及变更时还包含 `rollback_plan`。只提供方案，不代替人类执行线上变更。

### 2.9 修复后的验证建议

围绕原症状和根因定义成功标准，按需覆盖：

- 原失败路径是否恢复，正常路径是否未受影响。
- 关键指标是否回到基线，观察窗口是否覆盖原故障周期。
- 是否产生数据不一致或新的下游异常。

不要求无关的全量测试，也不把「没有报错」单独当作修复完成的充分证据。

### 2.10 需要补充的回归测试点

从根因推导回归点，优先覆盖触发条件、并发或异常恢复、关键边界值。测试点应能被具体用例验证，不写「加强测试」「避免再次发生」。

## 3. 验证策略

优先形成一条可检查的时间线：症状开始、最近变更、告警触发、用户反馈和恢复。随后用全局视图确定范围，再追踪一个代表性失败请求，找到第一个异常节点。

常用方法：

- **对比**：故障前后、正常与失败请求、不同版本或环境。
- **分层**：客户端 / 网关 → 服务 → 内部依赖 → DB / Redis / MQ → 基础设施。
- **关联**：对齐指标突变、错误日志、告警和变更，但保留因果验证。
- **证伪**：优先做结果能明确区分两个竞争假设的查询。

证据类型、适用场景和详细操作见 [验证方法工具箱](references/investigation-toolbox.md)。

## 4. 收敛与输出

- **根因已交叉验证**：使用 `incident-templates` 的 `diagnosis-report`；需要行动时再接 `action-plan`。
- **证据不足但仍可推进**：给出当前最可能假设、已排除项和下轮验证，不输出确定根因。
- **需要用户补充或裁决**：使用 `interim-conclusion`，只问会改变下一步的关键问题。
- **简单排查**：直接给结论、证据和必要下一步，不强制展示完整 10 步或套用正式模板。

## 5. 技能协同

1. 用 `incident-templates` 的 `triage-intake` 判断输入是否足以开始；基本可用时记录未知项继续。
2. 需要服务或拓扑背景时加载 `project-context`；已知缺陷对账使用 `tapd-inspector`。
3. 根据假设选择日志、链路、指标、信令、DB、Redis、MQ、发布和代码工具，不默认全查。
4. 用证据更新第 2.2–2.7 步，再决定结束、继续下钻或交回用户裁决。
5. 根因确认后才进入确定修复与回归设计；所有环境变更由人类执行。
