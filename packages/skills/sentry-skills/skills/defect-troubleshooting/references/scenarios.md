# 专项场景清单

以下是候选检查项，用于避免遗漏，不要求每次全部执行或写进回答。根据症状、架构和已有证据选择，信息不足时标为未知。

## 1. 线上 P0 故障

优先确认：

- 核心功能受损方式、开始时间、持续状态和影响范围。
- 能获取时，保存代表性日志、traceId、截图或告警作为证据锚点。
- 受影响用户数或请求比例；无法可靠估算时给出口径和未知项，不编造数字。
- 最近变更和可逆的临时止损选项，并说明副作用、验证标准与 `rollback_plan`。

需要对外沟通时使用 `incident-templates` 的 `incident-summary`。止损和长期修复分开描述，不把临时降级当作根因修复。

## 2. 性能问题

先确定是整体延迟升高还是尾部升高、吞吐量是否变化、从何时开始，再沿慢 span 或异常指标选择检查项：

- DB：慢 SQL、执行计划、锁等待、连接使用。
- 运行时：CPU、内存、GC、线程或连接池饱和。
- 缓存：命中率、热点 key、失效或击穿。
- 下游：超时、重试放大、队列等待、网络或跨服务延迟。

索引、缓存、GC、死锁和连接池只是候选原因，不应在没有证据时全部列为高可能性。

验证优先使用现有指标、链路和只读诊断。普通 `EXPLAIN` 与会实际执行语句的 `EXPLAIN ANALYZE` 要区分；后者及压测可能增加负载，只能在明确授权且风险可控的环境进行。

## 3. 数据一致性问题

优先记录：

- 不一致字段、期望与实际值、代表性主键和业务发生时间。
- 最早发现时间、影响范围和是否仍在扩大。
- 正常与异常样本在写入、事务、消息和缓存路径上的差异。

根据链路选择并发冲突、事务边界、异步任务失败、重试与幂等、消息乱序或缓存失效等待验证假设。

数据修复前必须确定正确数据来源、影响集合、校验方法和备份或补偿方案。修复脚本属于变更操作，只提供方案，由人类审批和执行。

## 4. 前端问题

先固定复现条件：入口与操作路径、浏览器、设备、操作系统、应用版本、账号或租户，以及问题是否稳定复现。

按证据选择：

- 接口状态码、响应内容、耗时和后端 traceId。
- 控制台异常、资源加载失败和前端代码路径。
- 浏览器兼容、缓存、Service Worker 或 CDN 差异。
- 正常与失败环境、账号、版本和请求参数对比。

清缓存、换浏览器和抓包用于区分假设，不应替代对具体错误证据的定位。
