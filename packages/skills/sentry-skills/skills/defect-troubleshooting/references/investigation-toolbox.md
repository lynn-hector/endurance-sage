# 验证方法工具箱

本资料用于设计缺陷排查第 2.5 步的验证方法。按假设选择手段，不依次执行全部检查。

## 1. 证据类型与作用

| 证据 | 最适合回答 | 使用注意 |
| --- | --- | --- |
| 日志 | 发生了什么错误，异常堆栈在哪里 | 单条日志通常只能证明该节点观察到了什么 |
| 链路 | 请求在哪一跳变慢或失败 | 先找第一个异常节点，再下钻其日志 |
| 指标 | 异常何时开始、范围多大、是否恢复 | 注意聚合维度和低样本量造成的误导 |
| 告警 | 哪些规则在同一时间触发 | 告警是症状或线索，不自动等于根因 |
| DB / Redis / MQ | 基础设施是否出现慢查询、等待、积压或消费异常 | 优先只读、小范围查询，避免增加线上负载 |
| 发布与配置变更 | 症状是否紧跟变更出现 | 时间吻合只是证据之一，还需验证影响路径 |
| 代码 | 实现是否能解释观察到的行为 | 确认代码版本与运行版本一致 |
| 已知缺陷 | 当前症状是否已有解释或修复计划 | 相似症状不等于同一根因 |

空结果只表示「在该环境、时间窗和查询条件下未观察到」。排除假设前，先检查环境、服务名、时间窗、时区、过滤条件和数据保留期。

## 2. 接到问题后的起步顺序

1. **确认真实症状**：区分误报、局部抖动、预期波动和用户可感知故障。
2. **对齐环境与时间**：确认 Session 环境、症状时间和时区，再建立查询窗口。
3. **建立时间线**：对齐症状、变更、告警、反馈和恢复时间。
4. **确定影响范围**：单请求、单接口、单服务、单集群，还是特定租户或地域。
5. **查看近期变更**：发布、配置、数据库和依赖服务变更；无变更时再重点考虑资源、依赖、流量和数据条件。

根据已有线索调整顺序。例如已有 traceId 时可直接追踪失败请求，不必先遍查所有指标。

## 3. 定位方法

### 分层定位

从客户端 / 网关到入口服务、业务服务、内部依赖、DB / Redis / MQ 和基础设施逐层判断：这一层是否异常，异常是自身产生还是下游传递。

只沿异常路径继续下钻，不为「完整」而检查所有层。

### 对比法

- 时间：故障前后、昨天与今天相同时段。
- 请求：正常与失败请求的参数、路径、租户或设备特征。
- 版本：当前与上一版本，同时确认部署时间。
- 环境或集群：只有配置和流量具有可比性时，差异才有解释力。

### 追踪单一请求

1. 用 traceId、requestId 或 callid 找一条代表性失败请求。
2. 还原各跳的耗时、状态和关键日志。
3. 找到第一个出错或异常变慢的节点。
4. 在该节点下钻日志、代码和依赖证据。
5. 再用其他请求或聚合指标确认它不是孤例。

### 关联分析

将同一时间窗内的指标突变、错误模式、告警和变更按时间排列。优先检查先发生且具有影响路径的事件；时间先后仍不足以单独证明因果。

### 假设验证

对每个竞争假设写出可观察预测，然后选择能同时区分它们的结果。例如「慢在 DB」与「慢在下游服务」可由同一 trace 中的 span 耗时直接区分。得到新证据后更新置信度，不只寻找支持首个假设的材料。

## 4. 常见误区

- 先钻单条日志，未确认影响范围和时间线。
- 把同时发生、时间相邻或相关指标直接判成因果。
- 查询窗口过大引入噪音，或窗口过窄漏掉关键事件。
- 空结果未检查查询条件，就宣布根因已排除。
- 只收集支持当前假设的证据，不主动寻找反证。
- 为执行完整清单而增加对线上状态有负担的查询或测试。
