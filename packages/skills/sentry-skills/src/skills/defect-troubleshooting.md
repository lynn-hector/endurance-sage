# 缺陷排查方法论

本文档是主排查方法论，用于「现象明确但根因不清」的缺陷排查。它以缺陷分析为核心流程，附录 A 已并入通用排查原则与证据收集方法。

工具映射：log-analyzer / trace-analyzer / metrics-inspector / db-inspector / redis-inspector / zadig-inspector / code-repository / mq-inspector 技能负责证据收集；输出模板见 incident-templates 技能；项目背景见 project-context 技能。

---

## 1. 核心原则

1. **不确定就问，不要猜**
   - 需求或症状有歧义时，列出所有可能的理解方向，让用户选择。
   - 证据矛盾时，给出替代假设，不强行统一成唯一结论。

2. **证据先于结论，结论先于行动**
   - 没有证据支撑的假设只配叫「待验证假设」。
   - 任何结论必须至少被两类证据交叉验证（日志 + 链路，或指标 + 代码）。
   - 先证明根因，再讨论方案。

3. **默认只读，不破坏线上状态**
   - 任何可能改变线上状态的动作必须明确标注风险、验证步骤和 rollback_plan。
   - 不代替用户执行回滚、重启、改配置、数据修复。

4. **区分关联与因果**
   - 多个异常同时出现不代表互为因果。
   - 必须通过时间线、依赖关系、调用链证明因果关系。

5. **先止损，后修复**
   - 立即止损优先于长期修复。
   - 所有变更必须有验证标准和回滚方案。

6. **一次只改变一个变量**
   - 同时做多个修复或验证动作，会混淆因果。

7. **任务 → 可验证目标**
   - 每个任务必须转化为可验收的输出。输入不足时追问，不编造输出。

## 2. 缺陷分析 10 步框架

分析一份缺陷报告时，按以下 10 个部分顺序填写。每个部分都有明确的红线：不能跳、不能混、不能含糊。

### 2.1 缺陷描述

缺陷描述 = 缺陷现象 + 影响范围。它是后续所有分析的输入，必须精确、可验证。

#### 缺陷现象

用「操作 / 期望 / 实际」三要素把模糊的「出 Bug 了」变成精确对比。

|维度|示例|
|---|---|
|操作|用户在下单页选择优惠券，点击「提交订单」|
|期望|2 秒内完成下单，跳转支付页|
|实际|转圈 10 秒以上，报「系统繁忙」，订单未生成|

**红线**：不能只写「系统有问题」或「接口挂了」。必须定义清楚「什么算不正常」。

#### 影响范围

给出严重程度和发生频率，帮助判断响应优先级。

|维度|应填写内容|示例|
|---|---|---|
|严重程度|P0 / P1 / P2 / P3|P0 致命，核心下单功能受损|
|发生频率|高频偶发 / 低频偶发 / 仅一次|今天 10:00 开始，多个用户反馈，非 100% 复现|
|影响面|用户量、请求比例、环境、租户|线上 20% 请求，所有租户|

**红线**：影响范围不能写「待评估」。必须给出严重性评级。

### 2.2 已知事实

这是整个分析的地基。每条事实必须附证据来源。

|事实|证据来源|
|---|---|
|页面转圈超过 10 秒|用户截图 + 客服反馈|
|最终报「系统繁忙」|用户截图|
|不用优惠券下单正常|部分用户反馈|
|问题从今天 10:00 开始|客服反馈时间线|

**红线**：没有证据的不能写进本节。「数据库有死锁」如果没有日志，只能放到第 2.4 节作为假设。

### 2.3 未知信息

列出「影响分析结论但目前没有答案」的问题。承认「我不知道」比假装「我都知道」更能加速排查。

|问题|为什么重要|
|---|---|
|精确复现路径：所有券都触发，还是特定券？|决定排查方向是通用逻辑还是特定数据|
|错误日志：接口返回什么错误码？后端有异常堆栈吗？|区分前端超时、后端错误、下游超时|
|影响版本：从哪个版本开始？昨天正常吗？|判断是否由变更引入|
|影响用户规律：所有用户还是特定设备 / 特定券类型？|判断是全局故障还是局部条件触发|

**红线**：不允许跳过本节。未知信息是后续排查的输入，也是向他人求助时的提问清单。

### 2.4 可能原因列表

至少列出 2–3 个可能原因，按可能性排序，每个必须附依据。

|可能原因|可能性|依据|
|---|---|---|
|优惠券抵扣接口慢查询 / 死锁|高|不用券正常 → 问题在券环节；转圈 10 秒 → 可能是 DB 锁等待|
|优惠券服务超时未降级|高|最终报「系统繁忙」 → 可能服务超时但熔断未生效|
|优惠券状态校验逻辑有 Bug|中|订单未生成 → 可能后端校验时死循环|
|数据库连接池耗尽|中|10:00 突然出现 → 可能批量任务占满连接池|
|前端传参错误|低|仅有理论可能，无直接证据|

**红线**：不允许只列 1 个原因。大脑天然倾向于「第一个想到的就是对的」，强制列多个就是逼自己跳出第一直觉。

### 2.5 验证方法

每个可能原因配一个验证方法，写清楚验证什么、怎么验证、预期看到什么、花多长时间。

|可能原因|验证方法|预期结果|成本|
|---|---|---|---|
|慢查询 / 死锁|查 10:00 后的慢查询日志，搜 coupon 相关 SQL|执行时间 > 10s 或有锁等待记录|低|
|服务超时未降级|看「提交订单」调用链，查 coupon-service 调用耗时和熔断状态|调用超时 + 熔断未触发|中|
|状态校验逻辑有 Bug|测试环境 Debug 模式复现，看是否卡在 `checkCouponStatus()`|线程卡住不动|中|

**红线**：验证方法不能写「检查一下」「排查一下」。必须具体到数据源、查询条件、判断标准。

设计验证方法时可参考附录 A 的证据优先级与定位方法。

### 2.6 推荐排查顺序

按「可能性 × 成本」排序，优先做低成本验证。

```text
1. 查慢查询日志 + 连接池监控（验证原因 1 和 4，5 分钟）
2. 查调用链监控（验证原因 2，10 分钟）
3. 测试环境加日志复现（验证原因 1/2/3，30 分钟）
4. 拉运维查 10:00 前后变更记录（找引入点，需会议）
```

**红线**：必须给出步骤 1/2/3，不能平铺所有可能原因让开发自己悟。

### 2.7 需要补充的信息

当前证据不够时，明确列出需要开发 / 运维补什么、怎么获取。

|信息类型|具体内容|获取方式|
|---|---|---|
|错误日志|提交订单接口今天 10:00 后的完整日志|ELK 日志平台导出|
|接口响应时间|P50 / P99 分布|APM 监控|
|调用链|失败请求的 Trace ID 完整链路|链路追踪平台|
|慢查询|今天 10:00 后 > 1s 的 SQL|DBA 或数据库监控|
|变更记录|10:00 前 24 小时的代码 / 配置变更|发布平台|

### 2.8 可能的修复方向

**只有根因确认后才写本节。** 如果根因还没验证，就写「根因待验证，暂不给出修复方向」。

根因确认后，给出不少于一种方案，让决策者选：

|方案|做法|优点|缺点|
|---|---|---|---|
|A. 优化慢查询|加索引 / 减 JOIN|根治|可能影响其他功能|
|B. 配置熔断降级|超时 2s 熔断，降级不校验券|快速止血|券校验失效需补偿|
|C. 临时禁用券|配置下发隐藏入口|5 分钟生效|影响体验|

**红线**：禁止基于假设直接改代码。必须先有根因，再给方案。

### 2.9 修复后的验证建议

修复不是结束，必须证明「真的修好了」。

|验证类型|内容|
|---|---|
|功能验证|正常流程 + 异常流程 + 边界值|
|回归验证|优惠券全量用例 + 下单流程全量用例|
|数据验证|检查有没有「订单生成但券没扣」的脏数据|
|监控验证|P99 响应时间是否恢复 < 2s|
|长期观察|观察 24 小时，关注有没有新的「系统繁忙」|

### 2.10 需要补充的回归测试点

最后一步，防止同类问题再犯。

|用例类型|测试点|优先级|
|---|---|---|
|并发用例|同一券并发用于 2 个订单，仅 1 笔成功|P0|
|异常恢复|优惠券服务超时 → 熔断降级生效，下单不卡住|P0|
|边界值|券面值 = 订单金额|P0|
|性能|优惠券抵扣接口 P99 < 500ms|P1|

## 3. 附录 A：验证方法工具箱

本节来自 `docs/methodology/general-troubleshooting.md`，作为 2.5 节「验证方法」的参考。设计验证方法时，可在此选择合适手段。

### 3.1 证据优先级

1. **日志**：错误堆栈、异常模式、traceId。
2. **链路**：慢调用、错误调用、跨服务依赖。
3. **指标**：QPS、延迟、错误率、资源使用率。
4. **告警**：已触发的告警和相关性分析。
5. **基础设施**：DB 慢 SQL、Redis 阻塞、MQ 积压。
6. **代码**：与错误信息相关的代码片段。

### 3.2 接到问题从哪开始

1. **确认是否为真实故障**
   - 区分误报、局部抖动、预期内波动。
   - 检查监控是否确实偏离基线，是否用户可感知。

2. **建立时间线**
   - 故障发生时间、最近变更时间、告警触发时间、用户反馈时间。
   - 时间线是判断因果关系的最强依据。

3. **查看全局视图**
   - 先看指标大盘，再看告警相关性，不要先钻某一条日志。

4. **锁定受影响范围**
   - 是单个接口、单个服务、某个集群，还是全量？
   - 是特定租户、地域、设备，还是随机？

5. **确认已知变更**
   - 发布、配置变更、数据库变更、依赖服务变更。
   - 如果近期无变更，重点考虑依赖故障、资源耗尽、外部攻击、数据异常。

### 3.3 定位方法

#### 分层定位法

从用户侧到基础设施侧逐层下探：

```text
客户端 / 网关 → 入口服务 → 业务服务 → 内部依赖 → 数据库 / 缓存 / 消息队列 → 基础设施
```

每一层先回答：这一层是否异常？是自身问题还是下游问题？

#### 对比法

- **时间对比**：故障前 vs 故障后，同时间段昨天 vs 今天。
- **环境对比**：线上 vs 预发，A 集群 vs B 集群。
- **版本对比**：当前版本 vs 上一版本。
- **请求对比**：正常请求 vs 失败请求，参数、路径、用户特征。

#### 追踪单一请求

拿到一个失败请求的 traceId 或日志标识，完整追踪：

1. 入口日志确认请求参数和返回。
2. 链路追踪确认每一跳耗时和状态。
3. 找到第一个出错或超时的节点。
4. 在该节点查看详细日志和异常堆栈。

#### 关联分析法

把同一时间窗口内所有异常列出来，按时间线排列：

- 指标突变（CPU、内存、连接数、队列长度）。
- 日志错误模式（异常类型、错误码激增）。
- 告警事件（依赖服务告警、基础设施告警）。
- 变更事件（发布、配置变更、数据迁移）。

寻找「先发生」的事件，它更可能是根因。

#### 假设验证法

1. 根据现象提出一个或多个假设根因。
2. 为每个假设列出可验证的预测。
3. 用数据逐个证伪或证实。
4. 优先验证那些「如果是真的，则很容易观测到」的假设。

### 3.4 常见误区

- 只看日志不看链路，容易误判根因位置。
- 只看指标不看日志，容易遗漏具体错误。
- 把同时发生的事件直接判定为因果关系。
- 忽略时间范围，查询过多无关数据。
- 在线上进行非只读操作，导致二次故障。
- 没有止损方案就直接修改线上配置或代码。

## 4. 质量红线

|类型|编号|红线|
|---|---|---|
|禁止|1|证据不足时直接下结论（「这就是 XX 导致的」）|
|禁止|2|把假设写成事实（「系统有 Bug」← 这是假设）|
|禁止|3|只列 1 个可能原因（至少 2–3 个，防确认偏误）|
|禁止|4|验证方法写「检查一下」（必须写检查什么、怎么检查）|
|禁止|5|修复方向写「优化一下」（必须写改什么、改哪里）|
|禁止|6|忽略未知信息（必须列出哪些还不知道）|
|禁止|7|不给排查顺序（必须给出步骤 1/2/3）|
|禁止|8|影响范围写「待评估」（必须给严重性评级）|
|禁止|9|可能原因不评级（必须标「可能性：高 / 中 / 低」）|
|禁止|10|遗漏需要补充的信息（证据不足时必须列补充清单）|
|强制|11|事实和假设必须分开（第 2.2 节 vs 第 2.4 节）|
|强制|12|每个可能原因必须有验证方法|
|强制|13|排查顺序按「可能性 × 成本」排序|
|强制|14|影响范围必须给出严重性评级|
|强制|15|信息不足时先追问，不强行分析|

## 5. 专项场景额外要求

### 5.1 线上 P0 故障

- 必须附截图或日志。
- 估算受影响用户数或请求比例。
- 给出临时降级 / 止损方案。
- 输出故障通报模板。

### 5.2 性能问题

- 必查：慢查询日志、APM 的 P99/P95、JVM GC 频率、资源使用率。
- 可能原因必须包含：索引缺失、缓存失效、Full GC、死锁、连接池耗尽。
- 验证方法必须包含：EXPLAIN 执行计划、压测复现、调用链耗时分析。

### 5.3 数据一致性问题

- 必须记录：最早发现时间、受影响数据量、数据不一致的具体表现。
- 可能原因必须包含：并发冲突、事务未提交、异步任务失败、幂等缺失、消息乱序。
- 修复方向必须评估：是否需要数据修复脚本、修复脚本的回滚方案。

### 5.4 前端问题

- 必须记录：浏览器版本、设备类型、操作系统、复现路径。
- 可能原因必须包含：接口异常、前端代码 Bug、浏览器兼容、缓存未清理、CDN 异常。
- 验证方法必须包含：清缓存重试、换浏览器复现、抓包看接口返回。

## 6. 与排查流程 / skill / template 的映射

```text
用户症状
    │
    ▼
triage-intake（incident-templates 技能）── 评估缺陷描述、已知事实、未知信息
    │
    ▼
defect-troubleshooting（本技能）── 选择方法论，收敛阶段与根因
    │
    ▼
log-analyzer / trace-analyzer / metrics-inspector / zadig-inspector ── 收集可观测性证据
    │
    ├──▶ db-inspector / redis-inspector / code-repository / mq-inspector── 执行第 2.4、2.5、2.6 步的验证方法
    │
    ▼
diagnosis-report（incident-templates 技能）── 根因 + 置信度 + 替代假设
    │
    ▼
action-plan（incident-templates 技能）── 修复方向、验证建议、回归测试点、rollback_plan
```

- triage-intake 的输出可直接套用第 2.1、2.2、2.3、2.7 节。
- 各 inspector 技能的执行结果填充第 2.4、2.5、2.6 节。
- diagnosis-report 负责把多个假设收敛为带置信度的根因。
- action-plan 负责第 2.8、2.9、2.10 节，且必须在根因确认后输出。
