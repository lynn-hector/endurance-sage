# mq-inspector：查询 RocketMQ 消息与消费轨迹

## 使用边界

通过 RocketMQ Console 查询指定 topic 的消息列表、消费状态与消息详情，排查消息积压、消费延迟、消息丢失或重复。触发场景：

- 用户怀疑 MQ 积压、消费延迟、消息丢失或乱序是问题根源。
- 排查流程中需要收集 MQ 证据。
- 日志/链路中出现 MQ 发送或消费异常。

跳过场景：

- 只讨论 MQ 架构或消息设计，没有要求查询具体状态。
- 缺少 topic 且无法推导。

执行原则：

- 只读操作，不执行任何修改 MQ 状态的命令。
- 积压高但消费 lag 低 → 可能是生产者突增；积压高且 lag 高 → 消费者能力不足或卡住。
- 多个 topic 同时积压时，优先考虑共同依赖（DB、Redis）异常。

Console 登录（JSESSIONID + XSRF-TOKEN 配对）由服务层自动管理，401/403 自动重登录重试，无需关心。

## 工具

### sentry_query_mq — 双模式查询

| 参数 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `topic` | 是 | - | topic 名 |
| `msgId` | 否 | - | 提供→查该消息详情与消费轨迹；省略→查消息列表 |
| `begin` | 否 | 1 小时前 | 列表模式：开始时间，毫秒时间戳或 ISO8601 |
| `end` | 否 | 当前时间 | 列表模式：结束时间 |
| `pageNum` / `pageSize` | 否 | `1` / `10` | 列表模式分页 |
| `keyword` | 否 | `""` | 列表模式：消息关键字过滤 |
| `dryRun` | 否 | `false` | 只返回构造好的请求，不发送 |

## 输出格式

统一 evidence 信封，`type: mq`。

**列表模式**：`data.messages[]`（消息原文）、`total_elements/total_pages`（总数/页数）、`task_id/truncated/scanned`（后台扫描任务状态——大时间范围查询是异步扫描的，`truncated: true` 表示扫描未完全覆盖）。summary 形如 `topic \`X\` 查询完成，返回 N 条，共 M 条，K 页`。

**详情模式**：`data.message_view`（消息体、key、tags、properties）、`message_track_list`（消费轨迹），以及三类消费组提炼：`consumed_groups`（已消费）/ `not_online_groups`（未在线）/ `filtered_groups`（已过滤）。

`confidence`：status=0 时 0.95，否则 0.5。

## 使用示例

```json
{ "topic": "topic_user", "pageSize": 10 }
```

指定时间范围（毫秒时间戳或 ISO8601）：

```json
{ "topic": "topic_user", "begin": 1785081600000, "end": 1785168000000 }
```

查单条消息详情与消费轨迹：

```json
{ "topic": "topic_user", "msgId": "7F0000010000D8130000000001234567" }
```

## 排查方法论

### 常见症状

消息消费延迟 / 队列积压 / 死信队列增长 / 消息丢失或重复。

### 排查步骤

1. **检查队列积压**：`sentry_query_mq` 列表模式看消息量和时间分布。积压高但 lag 低→生产者突增；积压高且 lag 高→消费者不足或卡住。
2. **检查消费延迟**：详情模式看各消费组的 `trackType`（CONSUMED / NOT_ONLINE / CONSUMED_BUT_FILTERED），未在线组持续存在说明消费者掉线。
3. **检查死信队列**：死信增长通常意味着消费端异常或重试策略不当（死信 topic 一般为 `%DLQ%{消费组}`）。
4. **跨数据源关联**：多个 topic 同时积压→优先查共同依赖（db-inspector / redis-inspector）；结合 log-analyzer 看消费异常堆栈。

### 典型根因

| 现象 | 可能根因 |
| --- | --- |
| 消费延迟 | 消费者处理慢、消费线程不足、依赖超时 |
| 队列积压 | 生产者突增、消费者不足、消费卡住 |
| 死信增长 | 消费异常、重试次数耗尽、消息格式错误 |
| 多个 topic 同时异常 | 共同下游依赖（DB/Redis）异常 |

### 止损建议

- 消费者能力不足：扩容消费者（评估资源）。
- 生产者突增：上游限流或削峰。
- 死信过多：修复消费异常，重投死信（谨慎操作）。
- 共同依赖异常：先解决下游依赖问题。
